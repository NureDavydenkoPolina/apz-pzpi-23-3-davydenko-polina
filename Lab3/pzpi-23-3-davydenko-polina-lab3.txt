2 ЗАВДАННЯ
	Метою даної лабораторної роботи є розробка front-end частини веб-застосунку для системи автоматизації ресторанного обслуговування SmartFood. Front-end повинен забезпечувати взаємодію користувачів із системою через веб-інтерфейс та підтримувати розмежування доступу відповідно до ролей користувачів.
	У межах роботи необхідно реалізувати два окремі інтерфейси: користувацький інтерфейс для клієнтів, що дозволяє переглядати меню, формувати замовлення та взаємодіяти з кошиком, а також адміністративний інтерфейс для персоналу закладу (адміністратор, кухар, офіціант), який забезпечує управління замовленнями та меню. Також система повинна підтримувати інтернаціоналізацію та локалізацію інтерфейсу.


3 ОПИС ВИКОНАНОЇ РОБОТИ
	У ході виконання роботи було розроблено front-end частину веб-застосунку SmartFood з використанням HTML, CSS та JavaScript. Архітектура клієнтської частини побудована за модульним підходом, де окремі файли відповідають за різні аспекти функціональності: взаємодію з API, логіку інтерфейсу, адміністрування та локалізацію.
	Користувацький інтерфейс реалізовано у вигляді веб-сторінки меню, яка отримує список страв із серверної частини через REST API та відображає їх у вигляді карток. Кожна страва містить назву, опис та ціну, а також кнопку додавання до кошика. Кошик реалізовано як модальне вікно, що дозволяє змінювати кількість товарів, видаляти позиції та переглядати загальну суму замовлення. Дані кошика зберігаються у локальному сховищі браузера, що дозволяє зберігати стан між сесіями. Процес оформлення замовлення реалізовано через послідовні запити до серверної частини: спочатку створюється замовлення, після чого до нього додаються обрані страви. Взаємодія з сервером реалізована через універсальну функцію запитів, яка автоматично додає заголовки авторизації та обробляє помилки.
	Для адміністративної частини створено окрему сторінку, доступ до якої здійснюється після проходження авторизації. Аутентифікація користувача відбувається шляхом введення email та пароля, після чого сервер повертає JWT-токен, який зберігається у localStorage і використовується для подальших запитів. Адміністративний інтерфейс підтримує рольову модель доступу. Залежно від ролі користувача (адміністратор, кухар або офіціант) змінюється доступний функціонал системи. Кухар та офіціант можуть змінювати статуси замовлень, а адміністратор має повний доступ до управління замовленнями та меню (створення нових страв, редагування існуючих та їх видалення). Для цього використовується модальне вікно з формою введення даних. Усі операції виконуються через відповідні API-запити до серверної частини.
	Інтернаціоналізація реалізована шляхом використання словників перекладів для української та англійської мов. При зміні мови інтерфейсу динамічно оновлюються текстові елементи сторінки, а також назви та описи страв. Обрана мова зберігається у localStorage, що дозволяє зберігати налаштування користувача.
	UML діаграма прецедентів відображає взаємодію користувачів із системою SmartFood відповідно до їх ролей. У системі визначено чотири типи акторів: Customer, Admin, Cook та Waiter. Користувач (Customer) має доступ до функцій перегляду меню, додавання страв до кошика, керування кошиком, перегляду замовлення та його оформлення. Адміністратор (Admin) виконує функції управління меню, перегляду замовлень, зміни їх статусів та видалення замовлень. Кухар (Cook) та офіціант (Waiter) взаємодіють із системою через перегляд замовлень та зміну їх статусів відповідно до бізнес-логіки системи. Усі актори мають доступ до функції зміни мови інтерфейсу.

Рисунок 1 - UML діаграма прецедентів (Use Case Diagram)
	Компонентна архітектура веб-застосунку SmartFood побудована за багаторівневим підходом, що включає клієнтський рівень, серверну частину та рівень бази даних. На клієнтському рівні реалізовано веб-інтерфейс користувача, який складається з двох основних частин: інтерфейсу для клієнта (Customer Web Interface) та адміністративного інтерфейсу (Admin Panel). Взаємодія клієнтського інтерфейсу із серверною частиною здійснюється через спеціальний модуль API Client, який реалізований у файлі api.js. Обмін даними відбувається за протоколом HTTP у форматі JSON. Серверна частина реалізована у вигляді REST API на основі Flask, яка обробляє запити клієнта, виконує бізнес-логіку та взаємодіє з базою даних. Рівень збереження даних представлений системою керування базами даних SQL Server, яка забезпечує зберігання інформації про користувачів, страви, замовлення та інші сутності системи.

Рисунок 3 - UML діаграма пакетів (Package Diagram)
	
	UML діаграма станів відображає життєвий цикл замовлення в системі SmartFood та переходи між його основними станами. Початковим станом є Created, який виникає після оформлення замовлення клієнтом. На цьому етапі замовлення стає доступним для персоналу. Після цього кухар розпочинає приготування, переводячи замовлення у стан Cooking. Після завершення приготування замовлення переходить у стан Ready, що означає готовність до видачі. Офіціант змінює стан замовлення на Delivered, завершуючи процес обслуговування клієнта. Діаграма також передбачає можливість повернення замовлення до початкового стану Created адміністратором у випадку необхідності корекції.

3  async function apiRequest(endpoint, method = 'GET', body = null) {
4      const token = localStorage.getItem('access_token');
5      
6      const headers = {
7          'Content-Type': 'application/json'
8      };
9  
10      if (token) {
11          headers['Authorization'] = `Bearer ${token}`;
12      }
13  
14      const config = {
15          method,
16          headers
17      };
18  
19      if (body) {
20          config.body = JSON.stringify(body);
21      }
22  
23      try {
24          const response = await fetch(`${API_URL}${endpoint}`, config);
25  
26          if (response.status === 401 || response.status === 422) {
27              console.warn("Сесія завершена або доступ заборонено");
28              handleLogoutSilently(); 
29              return;
30          }
31  
32          if (!response.ok) {
33              const errorData = await response.json();
34              throw new Error(errorData.error || `Помилка: ${response.status}`);
35          }
36  
37          return await response.json();
38      } catch (error) {
39          console.error("API Error:", error);
40          throw error;
41      }
42  }
